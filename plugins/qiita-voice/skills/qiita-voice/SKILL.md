# moritalous流 Qiita記事執筆スキル

このスキルは特定トピックの解説スキルではなく、**voice（文体・構成・トーン）の再現**が目的。
どんな技術トピックで頼まれても、このスキルが定める書き方のルールに従って執筆する。

## 手順

1. **必ず `references/style_guide.md` を先に通読する**。タイトルの付け方、構成、口調、
   絵文字の使い方、コード/画像/表の扱い、記事タイプ別の長さの目安まで、執筆時の判断基準が
   すべてここにある。この一覧を読まずに執筆を始めない。
2. **最初に記事タイプ（速報・発見型／中編／長編）を1つ選ぶ**（`style_guide.md`の表を参照）。
   軽い気づき・ちょっと触った程度のネタを無理に長編化しない。タイプが分量・コード数・
   画像数・見出し構成の目安を決める。
3. タイトルを考えるときは `references/titles.md` の実例パターンを参照し、近いパターンを
   1つ選んで内容に当てはめる。
4. 導入部・締めを書くときは `references/intros_and_outros.md` の「型」を借りる
   （実例の丸ごとコピペはしない。あくまでパターンの流用）。
5. 全体の雰囲気や「1本通しでどう書くか」を確認したいときは `references/examples/` にある
   5本の完全な実例記事を読む（短文・絶賛型、中量・技術検証型、長文・考察型、手順ガイド型、
   続編・実践型の5パターンをカバーしている）。
6. 下書きができたら、**必ず提出前に `references/avoid_ai_smell.md` で自己レビューする**。
   このスキルの出力は過去に「生成AIっぽさが残ってる」「見出しが胡散臭い」と2回指摘されて
   修正した経緯があり、そこで判明した「AIがバレる典型パターン」がここにまとまっている。
   ここを飛ばして提出しない。該当箇所があれば下書きの時点で自分で直してから出す
   （ユーザーに指摘されるのを待たない）。
7. 最後に「執筆後セルフチェック」で全体を確認する。

## 執筆時に必ず守ること（要約）

- 導入は1〜3文で終わらせ、すぐ本題に入る。前置きを長く書かない。
- 見出しは「まとめ」「手順」「環境」「動作確認」「おまけ」「参考」など、著者が実際に使う
  語彙から選ぶ（`style_guide.md`の一覧を参照）。**実験レポートのような番号立て
  （「1回目の修正」「原因調査」）や、「ほんとにあった」「なぜか〜になる」のような
  煽り・クリックベイト的な見出しは作らない**。この著者の見出しは「useChatの仕様が
  公開されている」のような素っ気ない事実の言い切り。大ぶりなH2を2〜3個並べる程度に留め、
  細かく分割しすぎない（詳細は`references/avoid_ai_smell.md`）。
- です/ます調をベースにしつつ、「〜かもしれません」「〜な気がします」「〜っぽい」といった
  断定を避けるヘッジ表現を**要所要所だけ**混ぜる。**同じヘッジ表現を3回以上連発しない**
  （毎文につけると逆に「AIっぽさ」の元になる）。杓子定規な敬語だけで通さないための
  リズム崩しは、ヘッジよりもむしろ体言止め・「。。」「w」・淡々とした言い切りで作る。
- **絵文字は基本的に使わなくてよい**（短編記事の約8割は絵文字ゼロ）。使うと決めた場合のみ
  同じ絵文字を3連続（🎉🎉🎉、😭😭😭など）にするのがこの著者の癖で、単発では置かない。
  淡々とした技術メモに無理に絵文字を足さない。
- `:::note`は補足・注意だけでなく「すごい！」のような**一言リアクション**としても使う。
- うまくいかなかった点・わからなかった点は隠さず正直に書く。取り繕った完璧な記事にしない。
- コードブロックの言語＋ファイル名注記（`` ```python:app.py `` ）は中編〜長編向け。
  短いコマンド1〜2行の速報記事では素の `` ```shell `` で十分。
- 締めは「## まとめ」で簡潔に総括するか、見出しなしの一言（「もうこれでいいです！」
  「めでたしめでたし。」）で締めるかのどちらか。長い総括を書かない。
  **「まとめ」を3点セットの教科書的な箇条書きにしない**。力の抜けた2〜3文の文章で流す方を
  基本にする。
- **結論をいちいち太字で強調しない**。太字はこの著者も使うが、機械的に「結論部分を毎回
  太字にする」ような使い方はしない。地の文に溶かして短く言い切る。
- **「〜が原因です」「〜だからです」という説明口調の因果接続を避ける**。原因や理由は
  接続詞で律儀につながず、そのまま地の文で言い切る（詳細は`references/avoid_ai_smell.md`）。
- タイトルには基本的に絵文字を使わない。テンションは「！」の数で調整する。
- **見出しは実測の頻出語彙（まとめ／手順／環境／おまけ／参考 等）から選ぶ**。
  「わかったこと・わからなかったこと」のような、著者が使わない説明的な見出しを発明しない。
- **画面操作を追う記事は1操作＝1枚のペースで画像を置く**。文字数が短くても画像は多くなって
  よい。地の文でスクショの内容を長々と説明で代替しない。
  - **実際にスクリーンショットを撮影できる状況（ブラウザ操作・スクリーンショットツールが
    使える等）なら、実際に撮影して`images/`ディレクトリに保存し、相対パスで参照する**
    （例:`![omikuji-result.png](images/omikuji-result.png)`）。
  - 撮影できない箇所（依頼者の手元の画面など、こちらから再現できない操作）だけ
    `![](ここにスクリーンショットを貼る)` のプレースホルダーにする。
  - プレースホルダーを1箇所でも使ったら、記事の末尾で依頼者に実際の
    スクリーンショットへの差し替えを促す一言を添える。全部プレースホルダーで
    済ませられるからといって撮影を省略しない。
- **事実と推測を混同しない**。コード・実行結果・画面の挙動は依頼者から実際に得た情報だけを
  書く。手元にない実行結果やログを想像で埋めない。情報が不足している場合は、記事を書く前に
  依頼者に確認する。

## 執筆後セルフチェック

- [ ] 記事タイプ（速報・発見型／中編／長編）を決め、その目安の分量に収まっているか
- [ ] 導入が3文以内で本題に入っているか
- [ ] 見出し語彙が著者らしい語（まとめ／手順／環境／おまけ／参考 等）になっているか
- [ ] ヘッジ表現（〜かもしれません等）が要所に数箇所ある一方、同じ言い回しを
      3回以上連発していないか
- [ ] 締めが冗長になっていないか（一言 or 簡潔な「まとめ」で終わっているか）
- [ ] コードブロックに言語・ファイル名を付けているか
- [ ] タイトルに「！」以外の過剰な装飾（絵文字の乱用等）がないか
- [ ] 見出しが実測の頻出語彙から選ばれているか（新しい見出し語を発明していないか）
- [ ] 画面操作を追う内容なら、地の文で説明を埋めずに画像プレースホルダーを置いているか
- [ ] 事実にない実行結果・ログを想像で書いていないか
- [ ] トピックに関係なく著者の型を守れているか（技術内容は依頼者の指定に従う）
- [ ] `references/avoid_ai_smell.md`の総合チェックリストを一通り確認したか
      （見出しの番号立て／煽り見出し／ヘッジ表現の連発／機械的な太字強調／
      説明口調の因果接続／教科書的な箇条書きまとめ、の6項目）

## 注意

このスキルが学習したコーパスはAWS/Bedrock/MCP/Claude Code等の記事が中心だが、これは
著者の関心の結果であり、スキルの制約ではない。依頼されたトピックがそれ以外でも、
文体・構成のルールだけを適用し、無理に元コーパスの技術要素を混ぜ込まないこと。
