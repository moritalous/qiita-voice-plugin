# moritalous流 Qiita文体ガイド（詳細版）

396本の公開記事を機械的な定量分析（見出し頻度、絵文字集計、行末表現、記事長分布）と
複数の並列レビューによる定性分析の両方で蒸留した、著者の文体・構成のルールブック。
執筆時はこのファイルを一度通読し、迷ったら該当セクションに戻ってくること。

## 大原則

- **速報性・実況感**：新サービス・新機能が出たら「早速試した」体で書く。理論の完成度より
  「今動かしてみた記録」であることを優先する。
- **失敗や限界を隠さない**：うまくいかなかった検証も正直に書く（「わからなかった」「TBD」
  「イマイチどのあたりがEKSなのか、わかりませんでした。。。」）。これが読者からの信頼と
  親しみやすさの核になっている。取り繕った完璧な記事にしない。
- **一次情報を必ず参照する**：公式ドキュメント・What's New・GitHubのURLをそのまま裸リンクで
  貼る（Qiitaのリンクカード化を利用）。孫引きせず、実機検証との差分を書く。
- **一テーマ一記事**：あれこれ詰め込まず、1つの技術・1つの検証に絞る。

## タイトルの付け方

最頻出パターン（優先度順）：

1. **「〜してみた」「〜やってみた」「〜試してみました」系**（全体の約2割、最多）
   - 例:「AWS IoT Greengrass 2.0が出たので早速試してみた」
   - 例:「1年遅れぐらいでGPT Researcherやってみたらもう最高！（マルチエージェント版もあるよ）」
2. **感嘆符でテンションを表現**（「！」「！！」「！！！」）
   - 例:「Jupyter AIが出た！試した！！すごい！！！」
   - 例:「AWS MCP Serverが普通に使えるようになったよ！」
3. **断定を避けた柔らかい言い切り**（「〜かもしれない」「〜という発明」）
   - 例:「2025年のAIエージェント開発の到達点はClaude Code on Bedrock AgentCoreかもしれない」
   - 例:「AWS CloudShell上でVSCodeを動かすという発明」
4. **カギ括弧「」で製品名・固有名詞を強調**
   - 例:「AWSが発表したAIエージェント構築SDK「Strands Agents」を5分だけ触ったあとに、もう5分だけ触ってみた」
5. **括弧で補足・条件・時期・オチを追加**（本題＋余談をタイトルに詰め込む）
   - 例:「AWSサービス一覧（2019/03版）※2022/12/29更新」
   - 例:「Docker MCP Gatewayがすんばらしい👌」（絵文字はごく稀に使うならこの程度）
6. **【】でジャンルをラベリング**（速報性・記事の毛色を先に宣言）
   - 例:「【未経験者大歓迎】RAG超入門」「【小ネタ】」「【速報】」「【ポエム】」
7. **比喩・パロディ**（既存の有名フレーズをもじる）
   - 例:「まるでDocker Desktop！！Rancher Desktopの登場です」
8. **疑問形は少数派だが、使うときは畳みかける口語調**
   - 例:「AgentCoreハーネス、プロンプトキャッシュが効かなくなくなくない？」

避けること：タイトルへの絵文字多用（本文とは対照的にタイトルはほぼ絵文字なし。装飾は「！」で行う）。
釣りっぽい大げさな言い切り断定（「〜かもしれない」程度の留保を残すほうがこの著者らしい）。

## 記事の構成

### 導入部（最重要・1〜3文で終わらせる）

前置きを長々と書かない。次のいずれかの型で即座に本題に入る：

- **前置きゼロ型**：「はい、できました🎉🎉🎉」「効かないと思います。無理やり効かせます。」
- **ニュース速報型**：「〇〇が発表されました」「〇〇がGAしました🎉🎉🎉」の直後に公式URLを裸貼り
- **共感の呼びかけ型**：「〜ってありますよね」「たまには〜したくなることもありますよね？」
- **前回の続き型**：「先日〇〇について投稿したところ、多くの反響をいただきましたので、第２弾です」
- **きっかけ提示型**：「久しぶりに〇〇したのですが、見慣れないボタンが。」

導入直後に構成図・スクリーンショットを1枚貼ることが多い（`![image.png](...)`）。

### 本文

- 見出しはH1（タイトル相当）→H2（章）→H3（手順細分化）のシンプルな3階層。
  厳密なMarkdown階層設計よりも勢い重視でよい。**ただし細分化しすぎない**：
  H2は「環境／やってみた／動作確認／まとめ／参考」のように2〜3〜5個程度の大ぶりな
  区切りに留め、「やってみた」の中の試行錯誤（原因調査、1回目の修正、2回目の修正…）は
  見出しで区切らず、地の文の接続（「〜と思って直しました」「これもダメで」）で
  進行を示す。実験レポートのように番号立てで細分化すると「AIっぽい」と検知される
  （実運用で実際に指摘された失敗パターン。詳細は`references/avoid_ai_smell.md`）。
- 頻出する章タイトル（頻度順）：「まとめ」「手順」「環境」「動作確認」「おまけ」「参考」
  「環境構築」「参考サイト」「準備」「終わりに」「やってみよう」「仕組み」「やってみた」
  **見出しはこのリストなど実測の頻出語彙から選ぶこと。「わかったこと・わからなかったこと」
  のような、著者が実際には使わない説明的・網羅的な見出しを新しく発明しない。**
  限界や不明点を書きたいときは見出しを立てず、末尾の`:::note warn`に一言でまとめる方が
  著者らしい（下記「締め」の項を参照）。
- **見出しで「釣ろう」としない**。「ほんとにあった」「なぜか〜になる」のような
  クリックベイト的・ドラマチックな煽りを見出しに使わない。実例集の見出し
  （「useChatの仕様が公開されている」等）はどれも素っ気ない事実の言い切りで、
  興味を煽る言い回しを避けている。
- 手順ものは番号付きステップ＋各ステップ直後にスクリーンショットの反復。
  **この「番号付きステップ」はMarkdownの番号付きリスト（`1.` `2.` ...）として書くもので、
  `### 1回目の修正` `### 手順2` のように見出しに番号を振ることではない**。試行錯誤や
  手順の各段階を見出しで細分化しない、という上記のルールと合わせて守ること。
- 「## 環境」見出しで使用ツール・バージョンを明記するのが定番（箇条書きで列挙）。
- 短い一文の説明→コードブロック→短い所感、のリズムを繰り返す。1文1行で改行し、
  段落間に空行を入れる（空行比率はだいたい全行の3割程度）。
- 補足・注意・つぶやきは`:::note` / `:::note warn`ブロックに入れる（半数以上の記事で使用）。
  ```
  :::note warn
  ただ、これで完璧かはわからないので、ご利用は計画的に！
  :::
  ```
- **`:::note`は「補足情報」だけでなく「一言リアクション」としても使う**のがこの著者の癖。
  地の文に混ぜず、感情や独り言をnoteブロックで隔離して置く。
  ```
  :::note
  すごい！
  :::
  ```
  ```
  :::note
  AIエージェントの型は、もうこれでいいんじゃね感。
  :::
  ```
  ```
  :::note
  マルチエージェント版の恩恵はよくわからず、かな？
  :::
  ```
- 長い実行結果・ソースコードは`<details><summary>実行結果</summary> ... </details>`で折りたたむ。
- 手順のスクリーンショット区間では、地の文の説明を最小化し
  **「一言説明→画像→一言説明→画像」の反復**にする（短編・手順ガイド型で顕著）。
  段落を長く書かず、1操作＝1文＋1画像で淡々と進める。
- 展開・結果を明かす直前に**三点リーダ「…」で溜めを作る**演出をたまに使う。
  - 例:「そしてこの状態でデプロイすると…\nPythonのライブラリーも含めてアップロードされます！」

### 締め

二系統ある。記事のノリで使い分ける：

1. **「## まとめ」見出し＋簡潔な総括**（最頻出）。基本は力の抜けた2〜3文の文章で流す。
   3点セットの教科書的な箇条書き（「- Aができました / - Bがわかりました / - Cが学びでした」
   のような律儀な総括）は機械的に見えるので多用しない。
   - 例:「## まとめ\nもうこれでいいです！」
2. **見出しなしの一言締め**（体言止め・感嘆一言）。
   - 例:「もうこれでよくない？」「めでたしめでたし。」「おしまい。」「すごい！」「素敵」
   - 昔話調の脱力オチ（「おしまい。」）も著者らしい締め方の一つ。

締めの後、必要に応じて：
- **「## おまけ」**でGitHubリポジトリへの誘導（「ソースコードはこちらです」「よかったら見てね」）
- **「# 参考」「## 参考サイト」**で参照元URLを列挙
- 読者への感謝・呼びかけ（「ぜひ使ってみてください！」「GitHubのスター、Qiitaのいいね、いただけると私がニヤニヤします」）
- 自著書籍の宣伝（『Amazon Bedrock 生成AIアプリ開発入門』）を「最後に宣伝」の見出しで挟むことがある
- 過去記事・関連記事・シリーズへのリンク

## 文体・口調

- ベースは**です/ます調**。ただし文末を体言止めや口語（「〜ですね」「〜んですよね」「〜っす」
  「〜だよ」）で崩すのが自然。杓子定規な敬語だけで通さない。
- 一人称は基本省略。使うときは「私」（「僕」はほぼ使わない）。
- **断定を避けるヘッジ表現**：「〜かもしれません」「〜な気がします」「〜のようです」
  「〜っぽい」「〜的な」「〜らしい」「〜んじゃないでしょうか」。**ただし1記事に数箇所、
  要所だけに使う味付け**であって、毎文につける主食ではない。同じ言い回し
  （特に「〜のようです」「〜らしいです」）を3回以上連発すると、逆に機械的な
  「生成AIっぽさ」として読者に検知される（実運用で実際に指摘された失敗パターン）。
  ヘッジを使いすぎたと感じたら、代わりに体言止め・短い言い切り（「0。」「毎回違う。」）に
  戻す方が自然。
- 「。。」「、、」と句読点を連ねて余韻・困惑・照れを表現する（例:「あまり理解はできてないです。。」）。
  こちらは口癖として多用してよい（ヘッジ表現より頻度を高くしてよい）。
- 文末に「w」を付けて自嘲・脱力を表す（例:「まだ高いw」）。
- 太字（`**`）はここぞという重要語にたまに使う程度。**「結論を出すたびに太字にする」ような
  機械的な使い方はしない**。太字なしで短く言い切る方がこの著者らしいことが多い。
- 自問自答・自己ツッコミを挟む（「実に難解なタイトルになりましたね。」）。
- 読者に同意を求める疑問形（「〜ですよね？」）を導入や中盤でときどき使う。
- **原因や理由は「〜が原因です」「〜だからです」という説明口調の接続詞でつながず、
  そのまま地の文で言い切る**（例:「Workersは、モジュールのトップレベルで動くコードだと、
  Spectre対策で`Date.now()`が常に0を返すみたいです。」のように、原因の説明とその帰結を
  律儀に接続せず並べるだけでよい）。

### 絵文字の使い方（重要な癖）

- **同じ絵文字を3連続で使う**のが著者特有のリズム。単発ではなく3連発を基本にする。
  - 達成・成功・リリース系ニュース：🎉🎉🎉
  - 困惑・落胆・自虐：😭😭😭 / 😫😫😫
  - 茶目っ気・ネタ：😝😝😝
  - 季節ネタ：🎄🎄🎄
- 比較表や手順の完了マークとしては単発で✅ ❌ ✓ ✔を使う（チェックリスト的用途）。
- 気づき・工夫のポイントには💡、驚きには✨をたまに添える。
- **タイトルにはほぼ絵文字を使わない**。本文中、特に感情が動いた行の直後・行末に置く。
- 絵文字を使いすぎない記事も多い（全記事の約1/3は絵文字ゼロ）。技術検証が淡々と進む記事では
  無理に絵文字を足さない。

## よく使う言い回し・接続詞

- 着手を示す：「とりあえず」「早速」「せっかくなので」「というわけで」
- 補足導入：「ちなみに」「ところで」「余談ですが」
- 順接：「なので」「そのため」
- 推測・伝聞：「〜のようです」「〜らしい」「〜と思われます」
- 謙遜・免責：「何番煎じかわかりませんが」「素人なので間違いがあればご指摘お願いします」
- 議論歓迎：「〜というご指摘を心の底からお待ちしております」
- 感想の定番：「いい感じ」「なかなか良さそう」「うまくいきました」

## コード・画像・表

- コードブロックの言語＋ファイル名注記（例: `` ```python:app.py ``）は**中編〜長編の
  実装解説系で使う書式**。速報・発見型の短いコマンド1〜2行程度なら、無理に付けず
  素の `` ```shell `` `` ```python `` で十分（実例記事でもそうなっている）。
- 差分は`diff`系タグ（`diff_python`、`diff_json`等）で変更前後を視覚的に示す。
- 1記事平均6〜8個のコードブロック、平均5枚前後の画像（多くはQiitaの画像ストレージ
  `qiita-image-store.s3...`のスクリーンショット）。手順の各ステップに1枚ずつ貼るのが定番。
- 比較・料金・仕様一覧はMarkdownテーブルで整理する（全体の1/4程度の記事で使用）。
- YouTubeデモは`<iframe>`埋め込みで示すこともある。

このコーパスはAWS/Amazon Bedrock/AgentCore/MCP/Claude/LangChain/Strands Agentsが中心だが、
**これは著者の関心の結果であってスキルの制約ではない**。どんなトピックであっても、

## 記事タイプ別の目安（最初にこれを選ぶ）

396本を文字数で3等分して集計すると、「短編」「中編」「長編」でコード/画像/絵文字の
使用量がはっきり異なる。**執筆前にどのタイプで書くかをまず決める**こと。全記事の
中央値だけを見て一律に長く書こうとしない（速報ネタを無理に長編化すると著者らしさを失う）。

| タイプ | 文字数の目安 | コードブロック数 | 絵文字ゼロの記事の割合 |
|---|---|---|---|
| **速報・発見型**（新機能に気づいた／触ってみた系の軽いネタ） | 〜3,000字程度 | 0〜2個 | 約8割 |
| **中編**（一般的な検証・実践記事） | 4,000〜7,000字程度 | 2〜10個程度 | 約7割 |
| **長編**（手順ガイド・考察・チュートリアル） | 8,000字〜 | 10個以上のことも | 約6割 |

判断の目安：
- トピックが「ボタンを見つけた」「ちょっと触ってみた」程度の軽い気づきなら**速報・発見型**。
  導入→事前準備→やってみた（スクショの反復）→軽い所感、で2,000〜3,000字に収める。
  コードブロックはあっても1〜2個。無理に「まとめ」節を立てなくてもよい。
- 手順を体系立てて説明する・複数の観点で比較検証するなら**中編〜長編**。

### 画像数は文字数ではなく「記事の種類」で決まる

画像数は速報／中編／長編という長さの軸とは**別の軸**で決まる。文字数が短くても
画面操作を追う記事は画像だらけになる。

- **画面操作・GUI操作を追うウォークスルー記事**（マネジメントコンソール、管理画面、
  IDE拡張機能の操作など）：**1操作＝1枚が基本**。2,000字程度の短い記事でも
  画像が10枚を超えることはごく普通（実例:「2026年、AWS LambdaはVSCodeで開発するのが
  ナウい」は本文2,677字に対し画像11枚）。地の文でスクショの内容を説明で代替しない。
- **コード中心・CLI操作中心の記事**：画像は0〜2枚程度で、コードブロックが説明の主役になる。

**手順区間を書くときのルール**：実際のスクリーンショットは書けないので、
1操作ごとに `![](ここにスクリーンショットを貼る)` のようなプレースホルダーを置き、
地の文は「〇〇をクリックします。」のような一文だけに留める。画像で見せるべき内容を
長い説明文で埋め合わせない（それをやると著者らしいテンポが失われる）。
プレースホルダーは依頼者が実際のスクリーンショットに差し替える前提であることを、
記事の最後に一言添える。

**絵文字は全体としては少数派**（短編記事の約8割は絵文字ゼロ）。「絵文字3連発」は
使うと決めたときの著者特有の癖であって、毎回入れるものではない。淡々とした技術メモでは
無理に絵文字を足さない方が自然。
